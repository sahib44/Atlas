# CSV import benchmark — 2026-10-29

Source: `a96eb26ce623165ec367c821b13508b95df372be`. Application implementation was unchanged.
This is a single-client local benchmark, not a concurrency, production, maximum-capacity,
or real-world matching-accuracy claim. No working-database connection, real contacts,
worker, or external email transport was used. The isolated database was removed afterward.

The 1,000-row workload against 1,000 existing contacts took **24.599 seconds median**
for upload + analysis + commit, range **24.276–26.165 seconds**, excluding review.
All 15 measured runs and three excluded warm-ups passed the correctness checks below.

## Reproduce

From the repository root with Docker running:

```sh
export MIST_SOURCE_REVISION="$(git rev-parse HEAD)"
docker compose --env-file /dev/null -p mist-deck-import-benchmark -f scripts/benchmark-imports.yml run --build --rm benchmark
docker compose --env-file /dev/null -p mist-deck-import-benchmark -f scripts/benchmark-imports.yml down
```

Use this standalone Compose file; do not combine it with the application's Compose
files. `--env-file /dev/null` avoids loading working credentials. The benchmark has
its own internal Docker network, no published ports, no persistent database volume,
and a 512 MiB PostgreSQL tmpfs mount. Its disposable database uses local trust auth
only within that network. The script refuses to reset anything except user
`mist_benchmark`, host `db`, database `mist_import_benchmark`, with the explicit
benchmark flag. It creates a random temporary login password that is never saved.
The runner mounts only its script and aggregate-results directory. It does not
start an email worker. Re-running overwrites the aggregate JSON results file.

## Fixtures and intended outcomes

Seed `20261029`. Each run resets the dedicated schema's application tables, then
seeds the same logical directory of **1,000 contacts**, fixed IDs, varied sampled
first/surname combinations, and 40 fabricated organization names. Names contain no
numeric uniqueness suffixes. Contacts use reserved `example.org` addresses.
Raw rows and mapping inputs are generated in memory; generated contacts/CSVs,
credentials, and database files are not saved. Hashes of each fixture and the
baseline are in the aggregate JSON and were stable across all six runs per size.
Database/authentication timestamps are regenerated outside the timed phases.

Each starting contact has an original note, historical address, qualification,
category, 2025 engagement, audit record, and frozen campaign preview. Those previews
are never queued. The CSV adds a 2026 engagement and a Mentoring qualification.

| Incoming rows | New | Exact email | Same name + organization, new email | Surname typo + same organization, new email | Invalid | CSV bytes |
| --- | --- | --- | --- | --- | --- | --- |
| 100 | 50 | 30 | 10 | 5 | 5 | 12,103 |
| 500 | 250 | 150 | 50 | 25 | 25 | 60,873 |
| 1,000 | 500 | 300 | 100 | 50 | 50 | 121,516 |

Exact emails vary case/whitespace. A typo omits the final surname character. Each
intended duplicate targets a distinct baseline contact. Invalid rows alternate
malformed addresses and nonnumeric years. Rows are deterministically shuffled.
Intended decisions: merge the known duplicates, create the known new contacts,
and skip invalid rows. Possible matches require human judgment in actual use;
the fixture's known identity is not evidence that a name heuristic proves identity.

## Actual limits and matching behavior

`imports.py` defaults to **2 MiB, 5,000 rows, and 100 unique nonempty headers**;
these runs used those defaults and did not approach the byte/row limits. Upload
requires UTF-8 (BOM accepted), sniffs comma/semicolon/tab delimiters, and validates
row shape. Analysis normalizes each valid row and scans the existing directory
plus preceding valid rows in the batch: approximately `O(ND + N²)` comparisons,
with name-comparison cost inside each comparison. It is not indexed matching.

`services.duplicate_match` returns exact-email 1.0, alternate-email 0.98,
normalized-name/organization 0.85, similar-name/same-organization 0.72, or
name-only 0.35. Similarity uses `SequenceMatcher` ratio >= 0.82. Scores are
heuristics, not probabilities. A row with any candidate score >= 0.7 must be
reviewed. Lower-scored candidates do not block commit. No application function
was replaced, cached, bypassed, or tuned for this benchmark.

| Incoming rows | Intended duplicate targets found | Rows requiring review | Incidental candidates >= 0.7 | Incidental name-only candidates |
| --- | --- | --- | --- | --- |
| 100 | 45 / 45 | 48 | 3 | 34 |
| 500 | 225 / 225 | 229 | 5 | 168 |
| 1,000 | 450 / 450 | 458 | 15 | 360 |

These counts were stable across repeats. Candidate counts and review-row counts
are different: one row can have multiple candidates. The 1,000-row fixture had
8 known-new rows additionally requiring review. Its 15 incidental strong
candidates were all `similar_organization`; they are false candidates according
to the fabricated ground truth. This is deliberately reported rather than
silently filtering similar names out of the workload. It is not a population-wide
false-positive or accuracy estimate.

## Timing method and review decisions

The runner starts **one unmodified Uvicorn worker** and uses sequential real HTTP
requests over container loopback. Timings use `perf_counter` around the complete
HTTP request/response, including normal authentication, middleware, application
validation, serialization, and database work. JSON decoding after receipt is not
timed. This bypasses the browser/nginx/host network, not the application routes.
Database migrations, fixture generation/seeding, login, correctness queries,
mapping, review, and repeat-commit checks are outside the three-phase total.

Each size runs one explicitly excluded warm-up, then five measured repetitions,
in order 100 → 500 → 1,000. Every repetition resets the logical database state;
OS/PostgreSQL caches and the API process are retained. These are warm measurements,
not cold starts or independent-machine trials. A 120-second per-request timeout
stops an unreasonably slow phase; no workload crossed it. No outliers were removed.

Mapping is saved through `PUT /api/imports/{id}/mapping`. After analysis, the
runner reads candidates for verification and uses ground truth to select the
expected candidate. It submits each decision through the actual
`POST /api/duplicates/{id}/resolve` endpoint: merge intended matches (selecting the
incoming job title), or create for incidental strong matches on new contacts.
It never directly changes a row's resolution in SQL. Weak incidental candidates
follow the application's existing commit behavior. The review calls are measured
separately; **their scripted speed is not human decision time**.

Every successful run checked exact batch totals and final contact counts; all
intended target candidates and invalid classifications; one merge snapshot per
update; preservation of every original contact's note, primary/historical addresses,
qualification, category, and 2025 engagement; unchanged original engagement,
preview, and audit records; preservation of original scalar values in merge
snapshots; and **zero outbound messages**. Imported 2026 engagements were expected
additions, not history loss. Repeating commit returned the same counts and left
contact, merge, import-row, audit, engagement, recipient, and outbound snapshots
unchanged. This checks retrying this committed batch, not arbitrary duplicate
uploads or every database-failure scenario.

There were **zero HTTP/correctness failures in the 15 measured runs** and all three
reported warm-ups passed. Two earlier harness setup attempts were excluded and
corrected before the complete series: a missing container `PYTHONPATH` prevented
startup, and an overly broad assertion incorrectly treated newly imported 2026
engagements as changed original history. No application implementation changed.

## Predicted manual time savings — assumptions, not measured impact

For this 1,000-row fixture, assume manual processing takes 30 seconds per row
(lookup/check plus entry/update), totaling **8 h 20 min**. Assume assisted work needs
5 minutes for setup/mapping, 20 seconds for each of 458 review rows, 30 seconds for
each of 50 invalid rows, 5 seconds to check each of 500 new contacts, plus ~26 seconds
of machine/mapping/review-request processing. That models **~3 h 45 min assisted**
and **~4 h 35 min saved**. Changing review time to 10–30 seconds gives roughly
**3.3–5.9 hours saved** under the other fixed assumptions.

This is a scenario calculation, not an observed efficiency improvement. It assumes
CSV data is already available, excludes collecting contacts/rules and training,
models only brief checks, and does not represent a timed comparison against an
experienced spreadsheet user. Real review complexity could erase or increase the
estimated saving. Do not put the predicted hours or percentage on a resume as fact.
